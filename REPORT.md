# REPORT — тестовое задание САП КОД AI-разработчик

## 1. Что было сломано

Я обнаружил, что исходный обработчик сохранял каждое входящее событие как новую заявку и создавал уведомление даже при повторной доставке. Уникальность пары `(source, external_id)` не обеспечивалась, входные поля не проверялись на тип и пустое содержимое, а пробелы по краям не удалялись перед сравнением.

### Что подтверждает лог до исправления

В моём логе первоначального запуска `python -m unittest discover -s tests -v` зафиксированы следующие несоответствия:

- `test_retry_is_duplicate_without_new_notification`: повтор вернул `{'status': 'created', 'id': 2}` вместо `{'status': 'duplicate', 'id': 1}`.
- `test_duplicate_after_reopening_database`: повторное обращение к той же базе также создало заявку с новым ID (`2` вместо `1`).
- `test_first_event_data_is_preserved_on_retry`: повтор с изменёнными `customer` и `message` был воспринят как новая заявка, вместо возврата ID исходной.
- `test_whitespace_is_trimmed_before_comparison`: значения с пробелами по краям не распознавались как та же пара ключей.
- `test_missing_customer_is_invalid_and_not_saved`: `customer="   "` привёл к статусу `created`, хотя ожидался `invalid`.
- `test_non_string_field_is_invalid`: числовой `external_id` привёл к статусу `created`, хотя ожидался `invalid`.

В логе я также увидел `ResourceWarning: unclosed database` и повторяющиеся `PermissionError: [WinError 32]` при удалении временных каталогов тестов в Windows. Причина — контекстный менеджер `with sqlite3.connect(...)` управляет транзакцией, но сам по себе не закрывает соединение. Я исправил это, добавив явное закрытие через `contextlib.closing`.

Мой лог заканчивается строкой `Ran 8 tests in 0.208s`; в нём нет итоговой сводки `FAILED` с точным количеством ошибок, поэтому я не указываю неподтверждённое итоговое число.

## 2. Что исправлено

Я внёс следующие изменения:

- Добавил уникальный индекс по `(source, external_id)`.
- Реализовал обработку повторной доставки через `INSERT ... ON CONFLICT DO NOTHING`; при конфликте возвращается ID исходной заявки.
- Добавил проверку полей `source`, `external_id`, `customer` и `message` проверяются на тип `str`, обрезаются через `strip()` и отклоняются, если после этого пусты.
- Настроил возврат статуса `{"status": "invalid", "reason": "..."}` до изменения базы данных.
- Сделал так, чтобы уведомление создавалось только для новой заявки; транзакционный контекст обеспечивает фиксацию успешной операции и откат при исключении.
- Добавил два собственных теста: значимость регистра `source` и отклонение события, которое не является словарём.

## 3. Как проверено

Для проверки я использовал команду из корня проекта:

```bash
python -m unittest discover -s tests -v
```

- **До исправления:** мой Windows-лог показывает шесть проваленных проверок утверждений (дубликаты, сохранение первоначальных данных, валидация и нормализация), а также ошибки очистки временных каталогов с `PermissionError: [WinError 32]` и предупреждения о незакрытых SQLite-соединениях.
- **После исправления:** я запустил тесты в среде подготовки; выполнение завершилось успешно: `Ran 10 tests in 0.101s` и `OK`.
- В итоговый набор входят восемь исходных сценариев и два добавленных мной: чувствительность `source` к регистру и отклонение события, которое не является словарём.

Результат после исправления подтверждён запуском команды в среде подготовки. Перед сдачей я должен повторить её в целевой среде, просмотреть изменения и убедиться, что могу объяснить реализацию.

## 5. Оставшиеся ограничения и риски

- Я не добавлял автоматическую миграцию старой базы: если в ней уже есть дубликаты по `(source, external_id)`, создание уникального индекса завершится ошибкой.
- Ошибки окружения или SQLite (например, недоступный путь к файлу базы) не преобразуются в статус `invalid`; этот статус предназначен для некорректных входных событий.
